# Внутризаводская перевозка — мобильный клиент (Flutter)

Приложение для рабочих-перевозчиков завода: список активных заявок на
внутризаводскую перевозку и карточка заявки. Данные читаются из HTTP-сервиса
опубликованной базы **1С:ERP** (только GET; кнопки действий будут включены,
когда на сервере появятся POST-эндпоинты).

- Экран входа открывается **при каждом запуске приложения** (рабочие на
  общем устройстве входят каждый под своей учёткой 1С, Basic Auth).
  Чекбокс **«Запомнить учётную запись»** подставит сохранённые логин и пароль
  в поля при следующем запуске — вход одним нажатием; без галочки учётка
  забывается при закрытии приложения. Ответ 401 возвращает на экран входа.
- Экран 1 «Список заявок»: pull-to-refresh + кнопка обновления, спиннер при
  загрузке, ошибка с кнопкой «Повторить», пустой список — «Нет активных заявок».
- Экран 2 «Карточка заявки»: секции «Груз», «Маршрут», «Условия» (скрыта, если
  пусто), «Требования», исполнитель и даты внизу; статус — цветной бейдж в AppBar;
- Кнопки карточки (доступность по статусу, сервер дополнительно проверяет сам):
  «ВЗЯТЬ В РАБОТУ» — активна, пока заявка не в работе и не ждёт мастера
  (POST /requests/take); «ВЫПОЛНЕНО» — активна только для заявки «В работе»
  (POST /requests/complete): сервер переводит её в «Ожидает подтверждения
  мастера» (или сразу «Завершена», если мастер не требуется) и создаёт задачу
  мастеру. Отказы сервера показываются текстом из `{"error": …}`.
- **Фото выполнения**: у заявок **в работе** с «ТребуетсяФото» на карточке
  отдельная кнопка **«СДЕЛАТЬ ФОТО»** (в других статусах она не показывается) —
  камера → снимок (JPEG ~1920px, качество 85) загружается
  в `POST /requests/photo?num=…` (тело — двоичные данные, сервер сохраняет
  как присоединённый файл заявки). Кнопка **«ВЫПОЛНЕНО» остаётся серой,
  пока фото нет**. Наличие фото проверяется запросом
  `GET /requests/checkphoto/{num}` при открытии карточки (и после любых
  действий): если фото уже есть — кнопка сразу показывает «ФОТО ДОБАВЛЕНО»,
  и «ВЫПОЛНЕНО» доступно даже после переоткрытия карточки. Неудачная проверка
  (сеть) трактуется как «фото нет» — рабочий может переснять.

Тестовый аккаунт: `testLog` / `7zyriqoL`.

## Требования

- Flutter 3.44 (stable) и Android SDK;
- Android-устройство с Android 6.0+ (minSdk 23);
- доступ к серверу 1С с устройства (HTTP, порт 80).

## Адрес сервера

Задаётся в одном месте — [`lib/api/api_service.dart`](lib/api/api_service.dart),
там **два адреса** и автоматический failover (по образцу проекта TSD):

```dart
static const String apiMobileUrl = 'http://81.211.118.58:8182/erp_local/hs/log'; // LTE (публичный, 8182 → этот ПК)
static const String apiBaseUrl = 'http://192.168.1.51/erp_local/hs/log';         // Wi-Fi / LAN
static const String apiFallbackUrl = 'http://localhost:8080/erp_local/hs/log';   // USB (adb reverse)
```

Приоритет: **мобильная сеть → Wi-Fi → USB** (как в «Регистрации нарушений»):
клиент перебирает адреса по порядку при сетевых ошибках, помнит последний
удавшийся; HTTP-ответы (401/404/400) переключение не вызывают.

- **Мобильная сеть**: `http://81.211.118.58:8182` — порт 8182 на роутере
  завода проброшен на этот же компьютер с базой (192.168.1.51:80), путь
  `/erp_local/hs/log`. Адрес работает только из интернета (LTE); из заводской
  сети внешние адреса завода недоступны (нет hairpin NAT), поэтому клиент на
  Wi-Fi молча пропустит этот маршрут (пауза ~5 сек на первом запросе после
  запуска приложения, дальше запоминается рабочий адрес).
- **Wi-Fi/LAN** `192.168.1.51` — компьютер с 1С в заводской сети. Сейчас
  заводской Wi-Fi (10.10.29.x) в локалку не маршрутизируется — нужен маршрут
  от ИТ. Путь к базе — в **нижнем регистре** (`/erp_local`): с `ERP_Local`
  Apache отдаёт 301, после которого POST превращается в GET.
- **USB** `localhost:8080` — проброс через кабель:
  `adb reverse tcp:8080 tcp:80` (слетает при переподключении кабеля).
- Если IP компьютера сменится (DHCP) — поправить `apiBaseUrl`; надёжнее
  закрепить адрес за компьютером у ИТ.

## Автообновление (как в проекте TSD)

Обновления хранятся в **публичной папке Яндекс Диска**: `manifest.json` +
каталог `releases/` с APK. Приложение после загрузки списка заявок тихо
проверяет манифест через публичный REST API Диска (без токена); если версия
новее — диалог с версией, примечаниями и кнопкой «Обновить»: скачивание
с прогрессом → проверка SHA-256 → системный установщик. Для `required: true`
кнопка «Позже» не показывается.

- Конфиг источника — `lib/update/` (`kUpdateConfig.publicKey` в
  `update_config.dart`): публичная ссылка папки
  «APK NO DELETE/Логистика» — `https://disk.yandex.ru/d/sfYHlEtcA-CJxQ`.
- Первый выпуск `1.0.1+2` выложен и проверен на планшете Active 7:
  приложение обнаружило версию, показало диалог с примечаниями, скачало APK,
  системный установщик обновил приложение (versionCode 1 → 2).
- **Публикация релиза** (версия в формате `1.0.1+2`, код версии должен расти):
  ```powershell
  # токен один раз: setx YANDEX_DISK_OAUTH_TOKEN "…"
  powershell -File scripts\publish-release.ps1 -Version 1.0.1+2 -ReleaseNotes "Что нового"
  ```
  Скрипт собирает release-APK (`--build-name/--build-number`), считает SHA-256,
  пишет `dist/manifest.json` и заливает на Диск: сначала APK, последним
  манифест. Ключи: `-Required` (обязательное), `-Format zip`,
  `-BuildOnly` (не выкладывать), `-InstallToDevice <adb-id>`,
  `-DiskFolder "APK NO DELETE/Внутризаводская перевозка"`.
- Release-сборка подписана debug-ключом (`signingConfig = debug` в
  `build.gradle.kts`) — обновления ставятся поверх установленных debug-сборок.
- Для работы установщика в манифесте уже есть `REQUEST_INSTALL_PACKAGES`
  и FileProvider; нативная часть — `MainActivity.kt` (MethodChannel
  `com.example.logistics/installer`).

## Запуск

```bash
flutter pub get

flutter devices            # убедиться, что телефон виден
flutter run                # на подключённом устройстве (debug, debug-подпись)
```

Готовый APK (debug-подпись, ставится без магазина):

```bash
flutter build apk --debug
adb install -r build/app/outputs/flutter-apk/app-debug.apk
```

Проверить связь с 1С и разбор ответа без запуска приложения:

```bash
dart run tool/check_api.dart testLog 7zyriqoL
```

## Установка на Xiaomi (MIUI)

`adb install` на MIUI падает с `INSTALL_FAILED_USER_RESTRICTED`, пока не выполнено:

1. войти в аккаунт Xiaomi (Настройки, самый верх);
2. Для разработчиков → **«Установка по USB»** — включить (после входа в аккаунт);
3. (опционально) там же **«Отладка по USB (настройки безопасности)»** — разрешает
   эмуляцию нажатий (`adb shell input tap`), если нужно управлять экраном с ПК.

## Если телефон не виден в adb

1. На телефоне: Настройки → Для разработчиков → включить **«Отладка по USB»**
   (сам «режим разработчика» недостаточен).
2. Выбрать режим USB **«Передача файлов (MTP)»**, а не «Только зарядка».
3. При первом подключении принять диалог доверия к компьютеру (RSA-отпечаток).
4. Проверить: `adb devices` — устройство должно быть в состоянии `device`,
   а не `unauthorized`.

## Особенности данных 1С (уже учтено в коде)

- Заявка содержит **несколько операций**. Список `/requests` отдаёт сводку:
  «Операций» (количество), суммарное «Количество» и «Транспорт» — карточки
  в списке показывают «Заявка № …», сводку, «🚛 Транспорт: …» («не указан»,
  если пусто), подразделение, требования и дату.
- Карточка `/requests/{Номер}` отдаёт массив «Операции»; каждая операция:
  «НомерСтроки», «Номенклатура», «Количество», «ККМ», «Откуда», «Куда»,
  «ТехнологическаяОперация», «ПЗ», «МаршрутныйЛист», «НомерОперации»,
  «НомерСледующейОперации» — всё показывается на экране карточки
  (документы-основания — мелким текстом).
- Карточка дополнительно отдаёт «Мастер» и «ПодтвержденоМастером» —
  показываются в подвале, если заявка требует мастера.
- Ключи JSON — русские; значения — строки-представления («Количество»
  приходит и числом, и строкой, и null), булевы поля — настоящие bool.
- Даты приходят как `«07.09.2026 9:55:14»` (час без ведущего нуля) или в ISO;
  пустая дата 1С (`«01.01.0001 0:00:00»` / `«0001-01-01T00:00:00»`)
  отображается как «—».
- Пустые строки (`Куда`, `ОсобыеУсловия`, `Исполнитель`, `Мастер`)
  → «—» / строка скрыта.
- Возврат с карточки заявки в список всегда обновляет список (статус,
  исполнитель, состав заявок подтягиваются сразу после «взять в работу» /
  «выполнено» / фото).
- После успешного автообновления приложение перезапускается сразу в список
  заявок: перед установкой запоминается ожидаемый versionCode, и если после
  перезапуска установлена именно эта версия и учётка была «запомнена» —
  выполняется автоматический вход (разовый; обновление не удалось или учётка
  не запомнена — обычный экран авторизации).
- Закрытые статусы («Завершена», «Перевозка не требуется», «Отменена»)
  отфильтровывает сервер; на случай, если он отдаст всё, фильтр продублирован
  в `ApiService.getRequests()`.
- 404 отдаёт `{"error": "Заявка … не найдена."}` — текст показывается пользователю.

## Фото выполнения (будущее)

Контракт `POST /requests/complete` предусматривал `{"num", "photo"}`; текущий
эндпоинт принимает только `num`. Мобильный клиент готов расширению:
`ApiService.completeRequest(num, {photoBase64})` уже умеет передавать фото —
останется добавить съёмку (image_picker) и включить передачу.
